# Verification: combine

How to run this file: the combine cluster is eight spectator and commissioner
screens around one live event, so the setup is a **combine you can drive**. Bring
the app up (`bun run dev` on a phone on the same network, or the deployed app,
which is the better surface for anything realtime) with an event marked active, a
roster of at least six athletes with names, fantasy teams and card art, and a
course of at least three named stations. Hold a **commissioner** session
throughout — the PIN or an admin account — because almost every state this file
asks for is reached from the admin console: marking a run official, editing a
time, scratching an athlete, re-randomizing, picking, closing voting, archiving.
Keep a second phone as an ordinary spectator, a third browser with site data
cleared for the guest items, and a laptop for the `/tv` and desktop rows. Work
each document in a block rather than flipping the event's state between rows.
Device values are as defined in [the protocol](README.md#devices-and-conditions).

**Twenty of the two hundred items in this file are marked `race day`** and cannot
be run before one: twelve in `live-timing.md`, four in `the-tv-board.md`, two in
`the-running-order.md`, one in `the-leaderboard.md` and one in `the-draft.md`.
Those are the items whose answer depends on athletes actually running — the
crowd's clock counting against a real start, celebrations arriving as people
cross the line, the field's tally moving under a thumb, and a board left on a
television for an afternoon. Everything else in this file, including every item
about an official run appearing, a time being corrected or a draft being picked,
**can be staged from the console** and is marked `commissioner` rather than
`race day`. Do not approximate a `race day` row with a staged one: the point of
the mark is that a rehearsal answers a different question.

Not checkable by hand:

- That the public read behind the board is column-scoped in the database, so the
  board can name a time and a penalty but has no access to a run's private notes.
  A grant, not a screen
  ([Interactions with other systems](../combine/the-leaderboard.md#interactions-with-other-systems)).
- Whether the signed artwork URL survives the export's cache-busting. The
  document pairs this with the tenth-of-a-second wait as the same question;
  `CMB-18` records the symptom, but the URL handling itself is not visible
  ([Open questions](../combine/the-leaderboard.md#open-questions-and-verification)).
- That no screen other than the admin screens writes an official time, so the
  board is never the source of a change it then has to redraw. An absence across
  the source ([Open questions](../combine/the-leaderboard.md#open-questions-and-verification)).
- Whether the app ever leaves two runs official for the same athlete. `CMB-12`
  stages it deliberately; whether the admin screens can produce it unaided was
  not established by the document either
  ([Open questions](../combine/the-leaderboard.md#open-questions-and-verification)).

  compose an out-of-order pick, which is precisely why a tester cannot make one
  ([Open questions](../combine/the-draft.md#open-questions-and-verification)).

  second position for the same athlete. `CMB-93` sees the error toast that
  results; the constraint is not visible from the phone
  ([Interactions with other systems](../combine/the-draft.md#interactions-with-other-systems)).
- The behaviour of a pick made while the picking order is changing underneath it.
  The document reasoned it from the code and did not reproduce it; provoking the
  exact overlap by hand is a race a tester cannot reliably win
  ([Open questions](../combine/the-draft.md#open-questions-and-verification)).
- That no screen other than this one writes a draft position. An absence across
  the source ([Open questions](../combine/the-draft.md#open-questions-and-verification)).

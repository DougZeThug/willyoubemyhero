# Verification: accounts

How to run this file: this cluster is about identity transitions, so the starting
state is the whole test. Begin every section from a **cleared browser** — clear
site data, which wipes the `wwbh:` keys and both IndexedDB databases and returns
the handset to a brand new guest. Clearing also spends a fresh daily secret, so
do it at the top of a section rather than between items. You need three things
standing by: a **spare member code** on a throwaway event's dummy participant
(never one of the thirteen paper slips — issuing or rotating a real code kills
the paper it was printed on, see B-01 and B-02 in [bug-triage.md](../bug-triage.md)),
a **throwaway email address** you can create accounts on and abandon, and a
**second handset** for everything about a collection surviving a phone. Two
items are mildly destructive and are fenced in their Setup: ACC-24 spends ten
attempts against a player's claim limiter, which locks that player's claim for a
few minutes and must be run on a dummy participant; ACC-27 rotates a code, so it
must be a dummy participant's. Device values: **phone** is the real surface;
**guest** is a browser with site data cleared and no player claimed; **member**
is a browser holding a member token from a paper code; **account** is signed in
with email and password; **commissioner** is an admin session, needed only where
an item stages something from the console; **second device** is a genuinely
different handset, because a second tab shares storage and IndexedDB and would
prove nothing; **offline** is airplane mode on the handset — the devtools offline
toggle does not fail an in-flight sign-in or an in-flight link the same way.

Not checkable by hand:

- **Whether email confirmation is switched on for the deployed project**
  ([Open questions](../accounts/signing-in.md#open-questions-and-verification)).
  The document describes the path with it on; which path the deployment takes is a
  project setting, not something the screen reveals.
- **The four attempts and their backoff, individually**
  ([While it runs](../accounts/signing-in.md#while-it-runs)). ACC-09 checks that
  the failure card eventually arrives; counting four attempts and measuring the
  backoff needs instrumentation.
- **The Google sign-in round trip.** It leaves the app entirely and comes back
  through an external provider; whether it returns to the right place depends on
  provider configuration outside this repository.
- **That no screen other than `/auth` reads the collection-link state**
  ([Open questions](../accounts/signing-in.md#open-questions-and-verification)). A
  negative over every screen.

Not checkable by hand:

- **Whether a failed upload leaves any visible trace**
  ([Open questions](../accounts/keeping-your-cards.md#open-questions-and-verification)).
  Every caller swallows it, so a hand tester cannot distinguish "did not run" from
  "ran and failed silently"; ACC-50 checks the claim survives, which is the part
  that is observable.
- **The 90-day member token expiry** ([Edge cases](../accounts/keeping-your-cards.md#edge-cases)).
  ACC-53 fakes the end state by deleting the token; watching a real expiry takes
  ninety days.
- **That the three named taps are the complete set of identity transitions that
  move a collection**
  ([Open questions](../accounts/keeping-your-cards.md#open-questions-and-verification)).
  A negative over every caller of the upload; a code search, not a pass.

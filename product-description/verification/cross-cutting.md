# Verification: cross-cutting

How to run this file: almost nothing here is reached by opening a screen. Each
item needs a **condition**, and producing the condition correctly is most of the
work. Four of them recur. **Offline** means putting the handset into airplane
mode — devtools' offline toggle is not equivalent and must not be substituted:
it does not fail an in-flight websocket the way losing the radio does, so it will
not produce the degraded feed state, and it lets a request fail instantly rather
than after the browser gives up, which is what several items are timing.
**Reduced motion** means the OS-level setting — Settings › Accessibility ›
Motion on iOS, Settings › Accessibility › Remove animations on Android — not any
toggle inside the app; the app has no such toggle, and finding one would itself
be a failure. **A second device** means a genuinely different handset: a second
tab shares storage and both IndexedDB databases, so it cannot show you what a
second device shows you, and several items here are precisely about that
difference. **A gyroscope** means a real phone with motion permission granted,
and the permission prompt is itself an item — once granted or denied it is
remembered per site, so clearing site data is how you get the prompt back.
Start each section from a settled, online, motion-on device with sound unmuted,
and restore that state before moving on. Nothing in this file is destructive;
the only state it changes is per-device — the mute flag, the trade seen-list and
motion permission — all of which clearing site data resets. Two items need a
**second person** with their own member session to send an offer, and the
race-day items are marked so rather than approximated.

Not checkable by hand:

- **Whether a real socket drop on a bad garden connection produces the banner
  promptly or sits in "connecting" for a long time first**
  ([Open questions](../cross-cutting/realtime-and-staleness.md#open-questions-and-verification)).
  The document names this as the most valuable item in the area but gives no
  threshold; airplane mode is a clean cut rather than the one-bar degradation that
  produces the interesting case.
- **That splits and penalties are not filtered by event**
  ([Edge cases](../cross-cutting/realtime-and-staleness.md#edge-cases)). The
  document says it is invisible while one combine is active, which is the only
  configuration that can be staged.
- **That no screen merges a realtime payload into its cache**
  ([Open questions](../cross-cutting/realtime-and-staleness.md#open-questions-and-verification)).
  A negative over every screen; a code search.

Not checkable by hand:

- **Contrast ratios** ([Open questions](../cross-cutting/accessibility.md#open-questions-and-verification)).
  They need a measurement tool against the rendered colours, not an eye; the
  "Reveal all" ghost and the small uppercase tracking are named as the places to
  start.
- **Whether the false "Pack Complete" heading is actually announced** depends on
  how a given reader treats a heading that changes in place
  ([Open questions](../cross-cutting/accessibility.md#open-questions-and-verification)).
  XCT-128 records what one reader does; it cannot settle the general case.
- **Whether the off-screen share composite is reached in practice** depends on the
  reader's handling of content positioned far off-canvas
  ([Open questions](../cross-cutting/accessibility.md#open-questions-and-verification)).
  XCT-127 records one reader's behaviour; that it is in the tree at all is the
  part that is fixable regardless.
- **That no component traps focus except the shadcn dialogs and menus**
  ([Open questions](../cross-cutting/accessibility.md#open-questions-and-verification)).
  A negative over every component, and `src/components/ui/**` is out of scope for
  this description.
